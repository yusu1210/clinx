# 复用上下文，不重复接入

[English](../en/project-context.md)

工程已知后，日常请求可以只是：“按这份 PRD 完成公告板需求，先确认关键方案，本地验证，不上线。”
不必再次提供仓库位置、知识入口地址和技术配置。Agent 从当前工程/任务、已有知识入口和本地绑定中解析。
这是 Skill 的执行规则，不是 CLI 已经能搜索私人系统。

## 入口接入一次

使用当前仓库指令、团队工程目录、已有工作区地图或获准使用的知识访问能力。
全新宿主没有可发现入口时，只补一个定位起点：工程、业务域或知识入口。
让 Agent 调查并在授权范围内保留有用链接，不要求用户先整理全公司工程清单。
安装 Skill 提供的是方法，不会自动让它知道私人位置。

例如，已有团队索引可以包含一小段导航：

```text
公告板 / 对外公告：
  规则归属：public-notices（规范工程链接）
  消费者：notice-reader（规范工程链接）
  契约与运行指南：链接到各自原有维护位置
```

这是示意，不是强制语法或已生成的平台绑定。本地宿主/工作区设置另行定位这些工程在本机的副本。
复用已有格式，不要求新增文件。相对路径适合稳定工作区布局；绝对路径可用于本机，但不是可移植的团队事实。

## 按信息归属维护

| 信息                                      | 维护位置                     | 何时按需复核                           |
| ----------------------------------------- | ---------------------------- | -------------------------------------- |
| 业务别名、能力、工程身份和关系            | 已有共享工程索引或归属方平台 | 相关归属、契约或仓库迁移               |
| 本机检出路径、协调目录                    | 已有机器/工作区绑定          | 换机器、路径缺失、身份不符             |
| 当前分支/worktree、未提交改动、进程和数据 | 当前环境及有用的任务交接     | 依赖该状态的动作前，以及相关变化后     |
| 构建、测试、运行方法                      | 原有工程指南、脚本和 CI      | 相关定义、依赖、目标或运行环境变化     |
| 协作偏好和持续授权                        | 适用的约定或原生策略         | 范围、有效期、身份、撤销或强制规则变化 |
| 单次任务批准与执行观察                    | 任务或原生平台记录           | 执行依赖动作时；不提升为永久权限       |

Agent 用可用工程/VCS 元数据和源码事实核验身份，不只看目录名。
remote 一致只能帮助确认仓库，不能决定使用哪个 worktree；Git 也不是强制要求。
凭据、带凭据的 URL 和个人文件系统细节不进入共享或公开知识。

稳定工程身份不代表消费者集合固定，也不代表运行态仍然有效。下一决策依赖这些事实时，
即使代码未变，也需复核相关注册、路由、目标配置与实际访问能力。
保存的平台观察只适用于对应目标和观察时间，不构成持续操作授权。

## 日常场景怎么处理

| 场景                  | Agent 处理                                         | 用户介入                          |
| --------------------- | -------------------------------------------------- | --------------------------------- |
| 熟悉产品的下一次需求  | 检索相关归属，复用本地绑定                         | 只给新增意图与变化的限制          |
| 熟悉工程的小修复      | 读取受影响代码和针对性测试，不全量调查或搭记录骨架 | 真正未决的取舍                    |
| 多工程协作            | 沿相关归属和消费者定位，选择本次子集               | 业务范围歧义，不是逐个 source ID  |
| 已知组织中的新工程    | 复用相关规范和访问方法，再做获授权的可运行切片     | 产品取舍；目标位置尚未确定时再补  |
| 换机器或目录迁移      | 沿已知本地迁移线索核验身份                         | 授权上下文无法定位时补本地起点    |
| 已存路径指向错误工程  | 停止依赖该定位，检查已知替代位置                   | 无法确定正确工程时澄清            |
| 多副本或多个 worktree | 遵守当前约定，保留无关工作                         | 无法消除且影响结果的副本选择      |
| 中断续接              | 定位原任务和当前变化，不重放旧操作                 | 任务选择歧义或决定变化            |
| 知识服务不可用        | 用可访问源码及当前权威材料继续                     | 只询问阻塞下一动作的必要事实/授权 |
| 只读依赖              | 阅读，并在获授权位置保留带条件的观察               | 必要改动与归属方协作              |
| 重复检查或发布命令    | 复用已审阅方法，核对相关变化、当前目标和权限       | 待批准操作，不重复确认每个参数    |
| 过期或冲突指南        | 检查受影响前提，在原归属提出或进行获授权修正       | 未决业务含义或共享发布批准        |

唯一且有充分依据的选择可在授权内继续，并让范围可检查。调查后仍有实质不同的候选，
集中提出一个带选项的问题。少问不等于更好：猜测写入目标比必要澄清更糟。
不为小任务全盘搜索、读取整个知识库、反复检查接入状态或刷新所有图谱。

## Skill、知识与 CLI 如何配合

`clinx-delivery` 与 `clinx-knowledge` 携带相同的
[上下文解析规则](../../skills/clinx-knowledge/references/project-context.md)。
知识提供导航和带条件的事实，Agent 核验当前适用性并使用已有工具。
知识读取权限不等于知识发布或工程操作授权；企业绑定留在可移植 Skill 发行内容之外。

CLI 记录有价值时，复用 `clinx.config.json` 和已审阅检查。配置包含无关工程时，显式选择任务 `sources`；
省略会绑定全部配置源。知识目录可以很广，但任务配置不是知识目录的副本。
包含未修改但真正相关的依赖，不只包含改动工程。

配置 `context` 用于导航，任务 `context` 绑定本地文件内容。引用相关归属并保留注明版本的决策依据，
不要绑定整个知识库或持续追加的任务日志。URL 本身不追踪远端变化。
路径变化不授权新目标，也不使旧证据自动适用。并行任务需要不同版本时，使用各自协调目录，不切换共享绑定。

`status`、`inspect` 和 `context` 提供本地诊断/导航，不会从远端知识服务解析业务名或替用户选择工程。
该流程由 Agent 执行。仅为了记住工程位置，不需要新增注册表、数据库、图谱或初始化 CLI。

## 如何验收复用确实有效

新会话只给正常工作区入口、真实形式的请求和完整 Skill，不给答案所在的工程路径。
检查工程身份、必要依赖、合理询问和无关工作保护。见原创[上下文场景](../../evals/context/README.md)。
准备脚本测试只验证输入，不代表 Agent 行为或实测收益。
声称覆盖真实 worktree、访问或知识服务故障前，应在对应环境补验证。
质量与安全是验收条件；重复输入、总调查工作量和维护量分开测量。
