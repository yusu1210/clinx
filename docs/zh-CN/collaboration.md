# 协作与授权

[English](../en/collaboration.md)

Agent 主导交付，不意味着每一步都要人工点击确认。需要约定的是：Agent 可以做什么、
哪些动作必须先确认、谁有权决定。企业既有规则和平台权限仍然适用。
这是由 Agent 遵循的工作约定，不是审批引擎，也不承诺 clinx 能阻止所有绕过行为。

## 多个参与者共用一份约定

默认一个主 Agent 对端到端结果负责，即使任务跨越多个仓库。保留既有团队的权责，
共享一份变化语义，不让每个仓库各自解释需求。委派是可选能力，须符合宿主和用户授权。

只为有边界的独立调查、互不冲突的改动或确有价值的第二视角引入其他参与者，
不把研发阶段机械复制成 Agent 层级。交接相关原始输入、当前约定、读写范围、依赖与所需证据。
通过现有工具协调共享文件与运行资源；代码隔离不意味着副作用隔离。

主 Agent 检查回收的实际结果、解决冲突并核对集成行为。约定发生实质变化时通知受影响参与者，
停止或调整已失效的工作。子任务的完成报告不是集成验收，委派也不能让待确认动作变成已授权。
详细执行规则见 Skill 的[协作步骤](../../skills/clinx-delivery/references/collaboration.md)。

## 分开约定两个问题

**交付到哪里**：技术方案、实现并本地验证、完成集成验证、发布就绪，或获得授权的发布及观测。
要求完成研发，不自动包含生产部署。

**哪里需要确认**：哪些决策或动作要先确认才能继续。要求确认技术方案，不等于后续每次修改都要确认。

| 协作方式       | Agent 自主推进               | 人或既有规则介入的位置           |
| -------------- | ---------------------------- | -------------------------------- |
| 授权范围内自主 | 当前交付目标内已授权的工作   | 重大未知、新的授权需求、强制审批 |
| 关键决策确认   | 调查及确认点之间已约定的工作 | 指定决策，例如实现前确认技术方案 |
| 分段确认       | 当前获准的工作包             | 进入下一个约定工作包之前         |

这些是自然语言协作预设，不是 CLI 参数、Schema 枚举或三套工作流。
可以组合使用：方案确认后自主实现与测试，发布仍遵守现有平台规则。
有效的预授权可以覆盖一类重复操作，不必每次点击；Agent 不能通过选择预设，
或在本地文件中写下“已批准”，为自己创造权限。

明确、低风险的任务直接沿用现有授权，不强迫用户填写启动问卷。
陌生且可能影响共享系统的变更，先调查，再提出必要的关键决策确认点。
判断依据是影响、可逆性、不确定性和既有规则，不是仓库大小。
即使任务简单，也要遵守用户明确要求的确认点；用户不能代替其他责任方豁免其强制审批。

## 可以直接使用的需求指令

```text
使用 clinx 交付 Skill，根据这份 PRD 和这些工程完成需求。
交付目标：实现并本地验证；不合并、不部署、不修改共享数据。
协作方式：关键决策确认。
先调查已有行为，形成技术方案。
实现该功能前请我确认方案；等待期间不要提前实现。
确认后，在约定范围内自主编码、测试、诊断和修复。
如果新发现会实质改变已确认的行为、兼容性、容量或恢复方案，再请我确认。
常规实现细节自行决定。交付实际证据与未完成的集成验证事项。
```

这里由需求发起人确认的是本地实现方案，不是生产发布。
如果操作需要其他责任方批准，应确认真正的审批人和渠道。
技术评审意见、另一位 Agent 的建议，都不能替代该动作要求的人工或平台批准。

自主处理小任务时，直接写需求和限制即可，例如：“更新这个文档示例并检查链接，
常规编辑不必确认；不要修改行为或发布。”无需先创建任务 JSON。

## 让确认具体、有效、可复用

对暂缓执行的动作，说明建议选择、相关替代方案、证据、重要未知，以及验证和恢复方面的后果。
明确谁能决定、确认什么：按需关联具体方案版本或变更、制品和配置、环境及影响范围。
保留真实决定的来源，适用时说明条件、有效期或复用边界；只维护一份当前约定。

确认后连续推进，不逐个询问函数或重构细节；若重要变化使原决策依据失效，再请求确认。
已批准方案内的代码修改不一定使方案批准失效，但针对某个发布制品的批准不能挪给另一个制品。

恢复任务时，到真实决定来源核对适用条件、撤销情况和目标身份。
本地哈希一致不代表远端审批仍然有效。沉默、超时、含糊答复或无法读取必要的审批状态，
都不能当成同意。

等待期间，只推进独立且已授权的工作。“确认后再实现”也不允许先写实现该功能的测试、
或在另一个分支实现，除非这些活动另有授权。没有可继续的有效工作时，准确交接待决事项。
被拒绝后停止相关动作，不能换一个工具绕过。

## 既有工具强制执行，clinx 保留上下文

权限、强制审批、职责分离由已有代码评审、身份和发布系统执行。
重要操作前，核对有效批准与实际目标、动作是否匹配。
拥有凭证、有部署 CLI、测试通过，都不等于获准执行。

需要可选 CLI 记录时，复用现有字段即可：

| 字段                     | 用途                         | 不代表什么                     |
| ------------------------ | ---------------------------- | ------------------------------ |
| `outcome`、`scope`       | 交付目标和范围限制           | 实现目标所需的一切操作都已获准 |
| `authority`              | 可做动作、确认边界、禁止事项 | 强制权限控制                   |
| `decisions`              | 协作方式、具体决定及真实来源 | 审批人身份或批准真实性已验证   |
| `context`                | 引用维护中的本地约定和方案   | 远端审批状态仍然有效           |
| `obligations[].external` | 保留由外部判断的验收条件     | 附加观察记录就能自动批准       |

任务引用的上下文参与本地输入绑定，文件变化会要求重新核对。
这只是在提示本地变化，不判断人工批准是否仍有效。`mode` 是工作类型，不是自主程度。
`--allow-external` 是显式执行开关，不是权限授予。
即使附件写着“通过”，外部条件在 CLI 结论中仍保持未决；真实授权要到原有系统确认。
