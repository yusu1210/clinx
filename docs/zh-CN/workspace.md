# 工作区布局与知识归属

[English](../en/workspace.md)

从现有工程和需求开始。工作区是协调一次交付的位置，不是新的开发环境，也不是强制的
仓库布局。单工程可以直接把自己的目录作为工作区；多个工程可以共用独立协调目录，
不需要搬迁或重新初始化各个工程。

根据谁拥有信息、信息随什么变化、谁需要读取它来选择位置。不要为了补全目录树创建文件。

## 哪些内容维护在工程自己的仓库？

仅属于某个工程、需要随它演进的长期事实，通常由该工程的负责人维护：接口契约、
不变量、构建测试方法、运行约束。与代码紧密耦合的文档，适合纳入同一版本与评审流程。
已有团队文档系统可以继续作为权威来源；引用它，不再维护另一份权威副本。

**clinx 不要求每个工程新增 `AGENTS.md`、`docs/`、系统地图或单独安装 Skill。**
下面的文件名是约定，不是前置条件。新建指令文件是可选的，遵守已有适用指令不是可选的。
核对 Agent 宿主的发现规则，显式读取所访问工程的适用指令；不要假设工作区入口会自动
加载兄弟工程的指令。

| 场景                         | 信息维护位置                                         | Agent 的动作                                                     |
| ---------------------------- | ---------------------------------------------------- | ---------------------------------------------------------------- |
| 有维护权限的工程已有有效指导 | 原有权威文件或文档系统                               | 读取并引用；通过正常评审修正相关错误                             |
| 有维护权限的工程缺少有用事实 | 代码、测试；后续任务确实受益时再补负责人评审的小文档 | 先调查，只补值得维护的信息                                       |
| 只读、第三方或其他团队的工程 | 保留原件；协调工作区记录带来源的观察                 | 写明来源、版本或日期、不确定性和复查条件；不冒充负责人确认的规则 |
| 关系跨越多个工程             | 对应团队维护的共享地图                               | 引用规则、状态、接口的负责人及消费者，不复制契约                 |
| 决策只适用于本次交付         | 当前任务约定或方案                                   | 留在任务内；可复用发现经过负责人评审后再沉淀                     |

缺少 Markdown 本身不是阻塞。代码、测试、CI 配置和原生工具同样可以提供所需事实。
但缺少必要语义、授权或访问权限仍然是缺口：文档可选，不代表调查和验收可选。
实现与契约冲突时，区分“当前实际行为”和“应当满足的行为”，向有权决策的一方解决
实质冲突，不能默认任意一份文件必然正确。

## 选择满足实际需要的最小布局

单工程或 monorepo 直接使用现有工程目录作为工作区，沿用已有文档位置与指令。
使用 CLI 时，其配置、任务记录和生成结果位于这个工作区下。

跨工程交付适合设置独立协调目录，避免把共享任务决策放进任意一个工程的名下。
兄弟目录是便于管理的默认选择；也可以沿用工程嵌套在工作区内的现有布局。
clinx 按配置解析源路径，不规定目录名，也不要求按前端、后端分仓。

```text
business-work/                        现有本地父目录；不要求 Git
  delivery/                          协调工作区；CLI --root 指向这里
    AGENTS.md                        可选宿主入口；已有则复用
    .agents/skills/clinx-delivery/    clinx init --agent codex --apply 安装时生成
    knowledge/                       可选共享导航，不是第二套代码库
      system-map.md                  引用能力与其负责人
    clinx.config.json                使用 CLI 记录时需要；init 不需要
    clinx/agent-entry.md              安装 Skill 时附带的可选入口
    .clinx/install/state.json         本地 Skill 版本、基线与文件归属
    .clinx/install/backups/           Skill 更新/移除保留的私密原文件
    clinx/tasks/change-123/
      contract.json                  CLI 任务约定
      prd.md                         可选本地需求，也可引用已有来源
      design.md                      可选任务调查与决策
      checkpoints/                   保存 CLI 交接记录时才生成
      revisions/                     修订 CLI 任务约定时才生成
    .clinx/                          CLI 生成的运行与证据记录；默认私有
  repo-a/                            独立维护的工程副本
    AGENTS.md                        仅当该工程采用它时存在
    docs/                            原有工程文档，如果有
    ...                              源码与原生工程文件
  repo-b/                            另一个工程副本；不要求补文档
    ...                              源码与原生工程文件
```

不用 CLI，就不需要 `clinx.config.json`、`contract.json`、检查点、修订记录和 `.clinx/`。
通过宿主支持的发现机制使用 Skill。没有反复跨工程查找信息的需要，也不必创建 `knowledge/`。
领域指南、术语表、链路图、操作指南可以解决重复问题，但不是首次任务的必填骨架。

配置最多声明 64 个源。指纹计算同时限制单源（50,000 个条目、128 MiB）和单任务聚合
（200,000 个条目、512 MiB），并顺序扫描各源。这些是安全上限，不是推荐规模。
应把 `inputs` 与 `exclude` 收窄到实质输入，并复用工程原生依赖图和受影响检查，
不要把整个组织的工程都列进一个任务。

如果工程嵌套在受版本管理的协调工作区内，应把这些工程副本排除在协调仓库的跟踪文件之外，
或沿用团队已有的仓库管理机制。不要误把源码历史纳入协调仓库，也不必仅为 clinx 引入
submodule。私有需求、决策和有用知识可以在访问范围合适的私有仓库中版本化，不应放进
公开的 clinx 源码仓库。两边都不能保存凭据。`.clinx/` 只是本地记录位置，不是安全边界；
需要控制访问、保留期限，并在分享前脱敏。

通过 CLI 管理 Skill 安装时，在本地保留 `.clinx/install/state.json`，用于安全更新，
不作为任务验收证据，也不应提交。`.clinx/install/backups/` 应保持私密。全局安装 CLI 不会在所有源工程创建
这些文件，见[安装生命周期](installation.md)。

## 区分任务输入与任务产出

维护一份当前约定。简单任务的需求和决策可以保留在会话或同一份文档中。
调查、方案和实施计划只有在篇幅、负责人或评审节奏需要时才拆分。
六个阶段文件不等于六份必交产物。

使用 CLI 时：

- `--root` 指向协调工作区。每个 `sources[].path` 指向实际工程副本，可以相对该根目录
  或使用绝对路径；检查在声明的源和 `cwd` 下运行。源可以是仓库，也可以是实际依赖目录。
- `clinx/tasks/<id>/contract.json` 是 CLI 的任务位置。已有 PRD、方案可以留在原处，
  通过引用接入，不必为目录树复制一份。
- 配置 `context` 是导航，按工作焦点筛选；源拥有的条目还按任务源范围筛选，工作区条目
  仍可入选。仅列入导航，不会把文件字节绑定到验收中。
- 任务 `context` 绑定被引用文件的字节。例如，使用
  `{ "source": "service", "path": "docs/contract.md", "why": "Consumer contract" }`
  直接绑定工程自己的契约。工作区文件路径相对 `--root`，不是相对任务目录。
  这些本地引用不会跟踪 URL 背后的内容变化；依赖远端资料时仍须核对其当前适用版本。
- 任务 `sources` 包含所有实质依赖，包括复用但不修改的源；保存时省略它会持久化当时的全部配置源，之后新增源不会静默扩大任务范围。
  它控制证据范围与导航选择，不是访问控制边界。
- 为源选择有意义的 `inputs`，排除生成结果。不要把持续追加的验证日志绑定为方案输入，
  也不能假定 `knowledge/`、任务目录会被自动排除。已绑定方案变化应触发重新核对验收，
  写入回执不应让该回执立即失效。

字段细节见 [CLI 参考](cli.md)。源范围记录的是声明，不能证明调查已经找全依赖。
源路径只是本地定位信息；验收身份绑定源 ID、选择器、检查定义和内容，移动内容未变的工程副本本身不会让收据失效。

## 并行工作与续接

不同任务 ID 隔离记录，不隔离代码修改。不同协调目录也可能指向同一个工程副本。
并行实现应复用宿主或 Git worktree 机制，或约定互不覆盖的写入范围并由一人负责集成。
不同交付需要同一工程的不同版本时，使用独立协调根目录，各自指向对应工程副本。
不要在其他任务执行期间切换共享源路径：源路径是工作区级配置，不是任务级配置。

独立工程副本不隔离端口、数据库、账号和部署目标。需要明确身份、测试数据、并发使用
限制以及清理责任。集成后验证组合效果，再声明完成；各个分支单独通过不等于集成验收。
续接时先检查当前版本、未提交改动、未决事项和相关远端状态，再复用检查点。
clinx 记录不会锁住其他 Agent 的编辑器，也不负责强制执行平台权限。

## 从 PRD 与工程地址开始

1. 读取原始需求，取得已授权的访问，检查现有工程副本、版本与适用指令。
   不为“接入通过”而重写工程文档。
2. 单工程沿用现有目录；跨工程选择协调目录。通过宿主加载 Skill，不需要逐工程初始化。
3. 追踪需求链路与消费者。复用负责人维护的文档，只在工作区保留有用的跨工程引用和
   带来源的发现。
4. 约定结果、证据和授权，记录实质方案决策。使用 CLI 时，根据调查起草源、检查配置
   和任务引用，先审阅执行预览，再运行检查。
5. 实现并验证真实路径，单独保留任务证据。变更使长期知识值得更新时，在权威来源处维护。

[多源示例](../../examples/multi-source/README.zh-CN.md) 实现了这一布局，包含真实 HTTP
消费者、工程拥有的服务契约，以及没有文档骨架的复用策略源。
[动手教程](hands-on.md) 展示从需求到验证的完整会话。
Skill 安装见[项目接入](adoption.md)，确认边界见[协作与授权](collaboration.md)。
