# 架构与边界

[English](../en/architecture.md)

## 系统目标

clinx 的目标是在用户授权和工程真实约束内，帮助 Agent 可靠完成所要求的工程结果。
走完阶段、写下记录、调用某个工具或多个 Agent 意见一致都不是结果。正确行为、保留既有
义务、可恢复性和如实声明是约束；满足这些约束后，才优化调查、评审、执行和维护成本。

因此，系统连接四个接口，而不是强加第二套工程平台：

1. **输入接口**：用户要求与有效决定、当前源码和项目正常入口。它明确本轮终点是可评审
   方案、实现、集成证据、发布就绪，还是已发布并观察到的结果。
2. **调查接口**：要求的用户路径、变化语义的现有读写方，以及受影响状态与效果的生命周期。
   导航工具生成候选；源码、契约和运行观察确定含义。
3. **决策接口**：重要选择保留依据、新旧处理、可推翻它的观察，以及尚未解决的边界和因此
   暂停的动作。
4. **反馈接口**：实现证据或独立源码挑战把反例送回同一方案或改动，修正并复核受影响决定；
   可复用的认识回到已有维护者处。

可移植 Skill 负责这套过程；项目负责源码事实、命令、工具绑定和验收；宿主负责会话、Goal、
Agent 执行和强制权限；可选 CLI 保存有界的连续性与证据，不判断语义是否完整。评测应在受控
条件下比较可观察结果和总成本，不以指定执行轨迹或工具数量计分。

## 职责分配

用户需求与现有工程 → 宿主 Agent + `clinx-delivery` Skill → 已有代码、浏览器与平台工具。
需要确定性支持时再调用 CLI；CLI 不调用模型，不安装环境，不自动推进阶段。

独立知识工作使用 `clinx-knowledge`；交付沉淀与知识工作共用归属、检索与复核规则。
有用发现回到持续维护的测试、工具、决策或指南，让下一任务可以找到并重新核对。
代码智能索引是可选、可替换的导航辅助，不是预期业务规则的权威来源。见[知识工作](knowledge.md)。

Workspace 是 `--root` 选择的本地协调目录，可以包含一个或多个 Source，包括兄弟仓库或需求资料目录，
自身不必是 Git 仓库。各 Source 保留源码、领域事实与操作指南；工作区地图只链接原归属，不复制其文档。
`workspace.ts` 负责源与文件引用解析，`task.ts` 负责任务记录和续接，`install.ts` 负责可选 Skill 文件安装与生命周期。
`status.ts` 汇总只读本地诊断，隔离组件失败，不推断宿主发现、不自动选任务、不判定验收。
仅显式选择任务时才计算续接指纹。
`commands.ts` 维护命令帮助，`output.ts` 将同一结果呈现为文本或 JSON，`resources.ts`
定位安装资源并向新目录复制案例，不执行工程。
这些模块都不规划或调度 Agent。

## 仓库布局

clinx 源码仓库不是用户应用需要复制的工作区模板。

```text
clinx/
  skills/clinx-delivery/    可移植执行说明与按需读取的参考文件
  skills/clinx-knowledge/   知识入口及共享知识与导航规则的维护源
  src/                     可选 CLI 实现
  bin/                     可执行入口
  npm-shrinkwrap.json      源码开发与 CLI 分发共用的唯一依赖锁
  schemas/                 生成的 JSON Schema，模型归属 src/schema.ts
  templates/workspace/     用户协调工作区的可选文件
  examples/                可运行的已完成合成示例
  evals/                   原始任务、准备工具及评估方验收程序
  test/                    clinx、示例与评估器的回归
  scripts/                 构建、文档、包与发布检查
  docs/en/                 英文用户指南
  docs/zh-CN/              对应中文指南
  .github/                 仓库 CI 与依赖更新
  clinx.config.json         本仓库的自检配置
  clinx/tasks/project/     本仓库的自检约定
  dist/                    生成的 CLI 构建结果，不是手工维护的源码
  artifacts/               已忽略的本地发布候选，不隐式发布
```

`examples/` 展示已完成部分的用法；`evals/fixtures/` 提供独立交付试验的未完成输入。
评估器和参考解不能进入候选任务输入；两类目录都不代表生产资格验证结果。
根目录的 README、贡献、安全和更新记录保留标准仓库入口。
每份 Skill 都自包含。共享知识参考文件在 `clinx-knowledge` 维护，通过 `npm run skills:sync`
同步到 delivery；构建拒绝内容分歧。宿主专用展示元数据不改变方法，也不要求只能使用该宿主。

## 用户工作区

| 产物                                  | 归属与作用                                          |
| ------------------------------------- | --------------------------------------------------- |
| `.clinx/install/state.json`           | 本地 Skill 位置、版本、基线哈希与文件归属，不是认证 |
| `.clinx/install/backups/UUID/`        | 更新/移除前保留的原文件与安装状态                   |
| `clinx.config.json`                   | 工作区拥有的源范围、上下文索引与已审阅检查          |
| 既有地图与指南                        | 由原归属方维护的源事实、导航与操作步骤              |
| 可选工作区地图或指南                  | 跨源导航和协调步骤，链接已有归属方                  |
| `clinx/tasks/ID/contract.json`        | 结果、范围、不变量、决策、权限、验收条件            |
| 任务 `context`                        | 引用的本地方案，其内容参与任务绑定                  |
| `checkpoints/NNNNNNNN.json`           | 输入绑定的续接说明，旧元数据仍可读，不表示完成      |
| `revisions/*.json`                    | 旧约定及原因、摘要，不回滚代码                      |
| `.clinx/runs/UUID/receipt.json`       | 本地执行记录，未签名、未独立认证                    |
| 同目录 stdout/stderr/XML              | 有界的原始执行输出                                  |
| `.clinx/evidence/ID/UUID/record.json` | 观察者声明与复制附件，不是验收结论                  |

交付记录模型由 `src/schema.ts` 定义，构建生成 JSON Schema。
重复改进时，外部 Goal/编排器负责预算、权限和是否继续。在普通 summary/next/blockers 字段中
留存假设与观察。新检查点不再接受结构化 loop 元数据，旧记录仍可读取。
CLI 保存用户/Agent 的陈述，不拥有其真实性，也不运行 Agent。
CLI 额外检查交叉引用、唯一性和文件系统约束；只做 Schema 校验并不等价。
Markdown 保存推理，JSON 保存机器记录。支持 Skill、CLI 和 Schema，不提供独立 JavaScript SDK。

`clinx/` 保存可选工作区指引与任务记录；`.clinx/` 保存生成的执行日志和观察附件。
两种名称都不表示内容可公开：任务资料与日志同样需要保护。
**Workspace / 工作区** 协调交付，**Source / 源** 提供声明输入，二者都不必是 Git 仓库。
`validate` 核对结构和引用；`verify` 根据验收条件判断所选声明。
**Receipt / 回执** 记录一次执行，**Attachment / 附件** 保存观察但不认证它。
详见 [CLI 参考](cli.md)。

地图和指南没有强制位置或文件名。只在确有知识缺口时使用[工作区模板](../../templates/workspace)；
源工程无需单独初始化或补齐统一文档骨架。详见[工作区归属](workspace.md)。

## 输入绑定与恢复

任务绑定规范化任务及显式引用文件的内容。
`{ "source": "service", "path": "docs/design.md" }` 直接读取指定源内文件；省略 `source` 则相对工作区根。
引用不能越出对应根目录或经过符号链接。
源指纹绑定声明路径、内容和可执行位。规范化 JSON 的键和源路径按 UTF-16 码元排序，
不依赖区域设置或 Unicode 排序规则。
执行记录保存前后指纹，核验时再检查当前输入和记录制品；检查点绑定任务、相关定义与源。
操作会读取当前配置，不盲信内存里的旧索引。

任务 `sources` 选择相关源 ID，省略时保守地包含全部配置源。范围必须包含相关依赖和消费者，
而不只是改动源或检查执行目录。任务中检查和源文件引用都必须属于该范围；调查改变范围时修订任务。

`definitionDigest` 绑定源选择器（含路径和排除项）及检查的实际执行定义。
回执只绑定所选声明的检查；其 `definition` 快照完整保存相关源选择器和检查，
不依赖今天的配置即可核对摘要与内部引用。保存定义损坏时，解释保持未知，不能重建为通过。
当前选择器或检查变化，不改写完整历史定义所描述的那次执行。
检查点和附件绑定任务引用的全部检查。
导航、工作区名和检查描述不参与。若显式把配置文件列入源 `inputs`，仍绑定其完整字节，不偷偷改写选择器。
核验用保存的检查定义解释历史报告，再对比当前绑定，陈旧的历史通过不会升级为当前通过。
不合并多次回执，也不推断检查依赖图。任务范围是需要审阅的声明，不是完整性证明。
记录还绑定所选声明：即使检查有重叠，修改 `--claim` 也不能把较窄的执行升级为更广验收。

输入列表必须明确，没有默认全量扫描。仅显式排除生效；直接指定的输入不能同时被排除。
目录名与 gitignore 不隐式改变范围。修改约定保留原 JSON，不抹去旧执行记录或把所有工作退回起点。

修订严格核对新约定与当前检查、引用文件；旧约定仅核对自身结构、内部关系和任务身份，
不要求已经过时的检查或方案路径仍可用。历史的 `previous` 保留原始 JSON 值；
`previousContractDigest` 是该 JSON 规范化后的摘要，不包含旧引用文件；
`nextDigest` 绑定新约定和当前引用。CLI 不使用今天的字节伪造历史输入绑定。
需要恢复方案历史内容时，沿用原工程的版本管理。损坏或身份不符的旧约定需要明确修复，
修订不是强制覆盖入口。

观察附件在验收计算之外，保留失败与不确定结果，不用新“通过”覆盖它们。
完整性与采集时本地绑定不表示真实目标版本或远端状态有效。

写操作使用工作区级排他锁；新文件先写入并同步到同目录私有临时文件，再用排他硬链接发布最终文件名，
不覆盖已有目标，读取者不把临时文件当记录。写入与读取采用相同的每文件 8 MiB 上限。
文件系统需支持硬链接；不退化为不安全的覆盖，也不保证完整的掉电持久性。
修订先保存旧约定再替换指定文件。
Skill 初始化先查冲突并记录文件归属；更新/移除先检查全部受管路径，保留原文件，最后发布安装记录。
可捕获的写入失败尝试回滚，不覆盖并发编辑；不接管、覆盖或删除用户所有的文件。
多文件写入不保证崩溃原子性，恢复前核对安装记录与备份。
案例只复制到新目录，失败时保留部分副本供检查，详见[安装生命周期](installation.md)。
崩溃后不自动抢锁。详见[CLI 恢复](cli.md#恢复)。

任务发现逐项隔离错误。最新检查点损坏时显式报告并要求对账，不静默选择更早的说明；
明确创建新检查点会越过损坏序号，保留原文件。
记录访问与源根解析分开：源根不可用时，当前绑定未知，已有历史仍可读取。
已移除的源或检查引用也不阻止读取结构有效的约定、交接和历史观察；开始新工作前，
先按当前定义修订约定。`task list` 和 `task show` 不要求配置有效；`evidence list`
即使配置无效或当前约定不可读，仍检查已存归档，将本地绑定标为未知。
需要当前配置或约定的命令仍拒绝无效输入。
执行和采集新绑定仍要求输入可用。详见[恢复](cli.md#恢复)。

## 结果格式与执行

`exit-code` 只说明命令是否退出零，不推断运行过测试。
`junit` 处理有界 XML，拒绝 DTD/实体、计数矛盾、重复身份和未支持的套件级失败/跳过，
区分失败与跳过，检查预期用例和最低数量。支持 Surefire 与 Node 报告的一部分明确结构，
不是所有 JUnit 方言；不支持的结果保持不确定。递归处理 `testsuite` 与 `testsuites`，
拒绝未知结构子元素。执行记录仅保存汇总计数，逐用例身份保留在原始 XML，
核验时重新解析，避免重复存储展开后的用例集合。

文件报告必须在本次命令中创建或改写，随后复制到记录目录。
这防止误用旧报告，不防恶意脚本重写旧 XML。
命令按 argv、`shell: false` 执行，原样保留空参数和纯空白参数，要求程序名非空白；
所有参数均禁止 NUL。显式调用 shell 仍是任意代码。
工作区内顺序执行检查，减少共享报告干扰，不是分布式调度器。
可执行文件保持原调用路径，包括符号链接与基于子进程 cwd 的 PATH。

## 限制

- 执行支持 macOS/Linux、Node 22.16+；方法与 Skill 不要求目标工程使用 Node。
- 不是沙箱：继承 PATH、环境、凭据、权限与网络；副作用声明不是强制权限策略。
- 有文件写权限者可伪造记录及哈希，无远端认证、签名导入或防篡改审计保证。
- 未声明或被排除的相关输入不在证据范围；依赖安装目录、工具链与远端状态不自动绑定。
- 每文件最多 8 MiB，每源 128 MiB、50,000 个条目（含目录），拒绝符号链接输入。
  大工程应按真实相关范围选择输入，不为通过而隐瞒依赖。
- 两次采样之间修改又恢复可能无法发现；`current` 不代表远端或整个工具链未变。
  产品版本和执行时记录的 CLI 运行环境是来源元数据，不与读取记录的机器做相等性比较。
  `protocolVersion` 标识证据解释规则，不支持的协议保持未知，不能通过。
  环境要求应由项目的真实检查或平台证据验证；工具链、容器和远端环境不自动锁定或重验。
- 每个输出流最多 2 MiB；被截断的 stdout JUnit 不确定。日志不自动脱敏，不能公开 `.clinx`。
- JUnit 文件路径为字面路径，不展开 glob；跳过与缺少预期用例不支持当前验收。
- 不同工作区的锁不协调对同一兄弟源的写入、IDE、人工操作或远端任务，需检查输入变化。
- 无内置浏览器自动化、企业接口、审批或自动发布；外部条件在 CLI 中保持未决。
- 文件系统并发攻击、脱离进程组的恶意子进程、强制终止或系统崩溃不在完整隔离保证内。

## 实现选择

TypeScript/Node 提供 CLI 运行时，JSON 定义可验证记录，Markdown 保存使用者与 Agent 指引。
执行复用项目已有命令。CLI 保持少量结果适配器，其他原生格式仍由项目工具负责。
新增接口需要具体用例、稳定边界与行为测试，详见[贡献指南](../../CONTRIBUTING.zh-CN.md)。
