# 接入已有工程、知识与工具

[English](../en/adoption.md)

先使用 [Skill](../../skills/clinx-delivery/SKILL.md) 和工程已有工具。
只有项目地图、操作指南或 CLI 配置能帮助当前或后续任务时才添加。
接入 clinx 不要求项目改用统一的目录结构。
首次使用见[从需求和工程开始](cold-start.md)。

## 决定哪些内容值得保留

多个工程只需选定一个工作区协调目录，在其中声明源根，不必逐仓初始化；单工程也可直接作为工作区。
各源的事实留在原文件，通过带 `source` 的上下文引用连接。任务范围包含受影响消费者和依赖，
不能只列修改仓库。可运行示例见[兄弟工程协作](../../examples/multi-source/README.zh-CN.md)，
绑定规则见[CLI 输入](cli.md#输入与初始化)。

每个工程的指令文件与地图都可选，不是接入条件。沿用已有指导；源只读时，可在工作区
保留带来源的观察。单工程、多工程布局、任务文档与并行边界见[工作区布局与知识归属](workspace.md)。

| 情况                 | 按需使用                       | 避免               |
| -------------------- | ------------------------------ | ------------------ |
| 简单局部任务         | Skill、已有工具、对话约定      | 强制文档树         |
| 陌生或反复使用的工程 | 带来源的小地图、实际操作指南   | 重复调查、过期抄本 |
| 长任务、歧义或跨工程 | 任务约定、决策引用、恢复检查点 | 完全依赖会话记忆   |
| 重复验证、证据交接   | 审阅后的检查定义与观察记录     | 把报告等同完整验收 |

优先沿用权威来源。缺失时可用[地图](../../templates/workspace/clinx/system-map.md)、
[指南](../../templates/workspace/clinx/local-guide.md)、[配置](../../templates/workspace/clinx.config.json)
和[任务约定](../../templates/workspace/clinx/contract.example.json)模板起草。
无需 CLI 记录时，可用[文字版任务约定](../../templates/workspace/clinx/task-brief.md)或已有方案，
不需要为使用方法论而编写 JSON。
示例路径不是工程必须具有的结构，使用前替换为已核实的事实。

地图定位能力、规则/状态归属、消费者和测试；指南保存命令/cwd、前置条件、身份、
目标、副作用、结果解释和恢复。业务规则仍留在原所有者处，一次性操作 ID 留在任务内。
保留来源、适用版本或最近观察，以及什么变化需要重核；不维护平行事实库。

## 衔接共享资产与既有流程

复用 Skill、规则或指南时，按需确认权威来源、维护者、适用范围和实际生效版本。
维护归属、检索可见性与执行权限是不同问题；个人偏好不能覆盖强制约束。
通过已有目录和入口按需读取，不把所有资产灌入上下文。同名或冲突副本按宿主明确的
优先级处理；重大冲突无法消除时，只暂停依赖它的动作，不自行发明覆盖规则。

已有交付流程适用时，把 clinx 的闭环融入其中，保持一个结果负责人和共同约定，
引用原生决策与状态，不再叠加阶段状态机或重复审批。安装 Skill、工作流标签和偏好
都不授予权限。相关资产变化后重核受影响的假设，不在无关交付中顺手升级全局工具。

通过资产所有者的正常评审路径推广有复用价值的发现，保留来源与边界，修正原处的
过期指引，不累积重复规则。一次成功的变通或高使用量都不足以证明应成为通用要求。
真实效果与采集边界见[评测](evaluation.md)。

## Skill 接入

`init --agent codex --apply` 写入 `.agents/skills/clinx-delivery`；
通用模式写入 `clinx/skills/clinx-delivery`，由用户明确读取或按宿主机制注册。
两者都包含许可和 `clinx/agent-entry.md`。先预览；存在不同文件则停止，不覆盖。

不自动生成地图、指南、任务或配置，不编辑全局设置或宿主指令，不热注册正在运行的宿主。
需要时把简短入口整合进已有指令。安装后应在选定宿主中核对发现结果。

## 用工程事实建立 CLI 记录

需要记录时由 Agent 写 `clinx.config.json`：

- 明确源根目录与相关输入，包括有意义的配置和锁文件。可显式引用兄弟仓库，不隐式扫描父工作区。
- 选择大目录时明确排除生成物和私密记录；目录名、gitignore 都不会自动决定证据范围。
- 引用已有或调查后补充的上下文，按关注点选择。
- 填入真实、可结束的检查命令，明确 cwd、结果语义与副作用。

通过 `verify` 预览选择范围，审阅脚本、目标与权限后再执行。
操作见[流程](walkthrough.md)，精确字段见[CLI](cli.md)。

## 企业已有 CLI 通常可以直接复用

现有 CLI/API/Skill 已提供操作时，不另包一层。仍需确定实际工程、环境、身份、
作用范围、终态/未知态和恢复方式。有部署命令不代表知道该部署什么，也不代表已获授权。

只有确有缺口才补薄的项目绑定、操作步骤、业务断言或访问/格式/可靠性适配，
能修上游时优先修上游。不要重复工具注册表，不把业务规则混入平台访问层。

私有流程、地址、标识与凭据留在私有工程或既有凭据系统。
平台返回成功不能证明项目业务不变量。按[协作约定](collaboration.md)明确权限与确认点；
既有审批系统仍是权威，本地通过结果或执行开关不授予生产权限。

从代表性任务开始，观察后续复用收益。保留真正改善正确性、执行或恢复的能力。
成本可用于可选取舍，不能作为删除必要验收或保护的理由。
