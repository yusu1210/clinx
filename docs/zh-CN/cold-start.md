# 从需求和工程开始

[English](../en/cold-start.md)

想先照着案例操作，阅读[完整实操教程](hands-on.md)：原始工程、Agent 请求、方案确认与同一任务的 CLI 会话。
本篇说明如何换成你自己的需求和工程。

提供需求即可开始；复用当前工程或已知知识入口，无法定位时才补仓库 URL 或本地目录。
Agent 会调查相关代码与工具，
无需你预先准备工程地图、技术方案、任务 JSON 或平台标识。
执行任务所需的访问权限与操作授权仍须明确。

## 可直接使用的请求

先[接入 Skill](installation.md)，或提供完整且已审阅的 Skill 目录的绝对路径。开始时无需 CLI 配置。

```text
在当前业务上下文中，按 clinx 完成 <需求文件或描述>。
先跟我确认关键方案，再实现并在本地验证。不推送、不部署。
告诉我如何使用结果，以及尚未验证的部分。
```

调查、复用、运行验证和交付说明已由 Skill 提供，不必每次在提示词中重复。
这里的方案确认是本次协作选择，不是所有改动都必须经过的门禁；请写明你的实际边界。

如果希望先确认方案，在请求中写明“实现前请我确认”。Agent 可以先调查并准备方案，
确认前不实现。Skill 与上下文入口可被发现后，后续请求只需新增意图和变化的限制。
CLI 自身不下载 PRD、不克隆仓库、不调用模型。见[协作授权](collaboration.md)。

## Agent 实际负责什么

熟悉工程复用、换机器、多 worktree、知识服务故障、只读依赖等十二种日常场景，
见[上下文复用](project-context.md)。Agent 先解析已有事实，缺失或存在实质歧义时再集中询问。

源名称、检查定义、任务 ID、配置和回执路径由 Agent 处理，不要求用户填写，但保持可检查。
产品取舍、无法取得的凭据和待批准操作不能被隐藏或伪造。

重要任务可由 Agent 根据调查结果填写[简短任务约定](../../templates/workspace/clinx/task-brief.md)。
对话或现有方案同样有效，不强制另建文档，详细事实只有一个当前来源：

```text
结果与交付终点：
当前链路及证据 / 能力复用或缺口：
范围 / 规则与状态归属 / 变化的接口和不变量：
首个完整切片 / 实际命令与 cwd / 目标与身份：
验收条件 -> 真实消费者观察 / 反例 / 剩余缺口：
允许动作 / 待确认事项与责任人 / 停止与恢复：
```

运行路径应能由 Agent 使用，不预留成一句“用户自行测试”。
Skill 的[运行步骤](../../skills/clinx-delivery/references/runtime.md)说明如何使用原生反馈、
核验异步效果和不同版本消费者。

- 读取原始需求和附件，确认当前版本与已有改动；缺失重要来源时明确缺口，不用摘要假装读过原文。
- 用现有工具取得范围内的工程，保留用户选择的分支和已有目录，先读项目指令再执行代码。
- 追踪入口、规则/状态所有者和最终消费者，逐能力判断复用、扩展、组合、新建或未知。
- 从指南、CI、脚本和锁文件确定模块、运行时、命令与基线，审阅钩子；静态候选不代表就绪。
- 约定可观察的行为、负例、交付终点和权限；调查可以解决的事实不反复问人。
- 实现、观察和修复最小完整切片，最后回看原始需求，交付可复现结果及边界。

这不是六个必须由用户点击的关卡。未知事实先调查；未知产品决定和模糊共享目标不能擅自猜。
发现超范围依赖问题不意味着自动修复它。

## 新建能力与复用能力

新服务可以主要复用身份和存储，旧服务也可能增加新能力。应逐项判断能力，而不是给整个仓库
贴上“新建”或“改造”的标签。空工程从原始需求、参与者、工程约束和不确定依赖开始，
不要虚构已有调用链；第一条切片应先产生实际效果，再扩展脚手架。

复用既有能力仍需核对语义、权限、错误处理和实际支持的消费者版本。通用客户端可能无需改动
就能展示服务端结果，但刷新、空态、错误态仍要按需求验证；后端改动也不要求无差别重建所有客户端。

## 两种交付形态

| 决策       | 新建本地阅读清单                           | 复用已有批量偏好能力                          |
| ---------- | ------------------------------------------ | --------------------------------------------- |
| 用户结果   | 推荐图书、看到列表，有权限者标记已读       | 重置所选用户偏好，保持无关状态                |
| 调查重点   | 参与者、持久化期限、演示身份限制与已有约束 | 接收端重置语义、已有分批/重试能力及限额       |
| 第一条切片 | 提交 -> 真实 API -> 保存 -> 刷新展示       | 单个重置 -> 真实网关/接收端 -> 权威回读       |
| 范围内扩展 | 权限拒绝、输入校验、保存失败与重启         | 去重、容量、永久/暂时失败、结果未知与安全重放 |
| 验证       | HTTP、持久化和真实浏览器操作               | 原测试和接收端效果，不只断言 Mock 参数        |
| 交接       | 启动/使用/停止、演示限制与未验证目标       | 具体调用、部分成功/未知结果恢复和集成缺口     |

见可运行的[阅读清单](../../examples/reading-list/README.zh-CN.md)和原始[批量操作需求](../../evals/fixtures/bulk-reset/PRD.md)。
它们是合成例子，不是必选架构或 Agent 收益证明。按实际需求决定相关边界：
不为纯接口需求新增 UI，也不忽略结果依赖的未修改消费者。

## 在现有环境中执行

使用现有工具执行已审阅的依赖恢复、构建和测试。真实集成可能适合已有授权测试环境，
不必把全系统装到本机。工作区不隔离共享队列、端口或数据。

`clinx inspect` 只发现部分根目录脚本、Maven 候选和声明的检查，
不替代 JDK、模块、任务或 CI 配置的真实调查。未支持某工具链的静态识别，不妨碍 Agent 使用该工具链。

## 何时增加 CLI 记录

小任务直接使用 Skill；有复杂语义、长时间工作或交接需求，再由 Agent 编写任务约定和配置。
初期可使用对话或普通任务约定；确需 CLI 记录时，声明真实需求或方案文件，代码出现后再加入输入。
不要为了初始化 clinx 创建占位源码、虚构测试或搭建整个环境。
工程地图与指南按可复用价值建立，优先引用现有来源。
浏览器或外部观察可保存为[附件](evidence.md)，不会因此自动通过验收。
见[项目接入](adoption.md)与[评测协议](evaluation.md)。
