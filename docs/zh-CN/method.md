# clinx 全栈研发方法

[English](../en/method.md)

先明确用户需要发生什么，再调查产生该结果的代码和工具。
改动可能只涉及一个组件，也可能跨多个组件；只有需求需要时，才涉及页面、服务、数据库或部署。
新建工程、既有系统，以及新能力与已有能力并存的需求都适用。

本篇解释方法背后的判断依据。要直接开始真实任务，请阅读[从需求开始](cold-start.md)；
要按可运行案例练习，请阅读[实操教程](hands-on.md)。

## 工作中反复核对的五个问题

**Discover / 调查 → Contract / 约定 → Build / 实现 → Verify / 验证 → Learn / 沉淀。**

| 步骤 | 要回答什么问题                     | 带着什么结果继续         |
| ---- | ---------------------------------- | ------------------------ |
| 调查 | 现有什么？行为和消费者由谁负责？   | 相关源码、差距和重要未知 |
| 约定 | 目标行为、范围、验收与权限是什么？ | 足以行动的明确决定       |
| 实现 | 最小完整链路能否运行？哪里失败？   | 穿过必要边界的工作结果   |
| 验证 | 受影响消费者是否满足原始需求？     | 当前观察、失败与缺口     |
| 沉淀 | 哪些发现能帮助下一个任务？         | 更新的测试或有用项目指南 |

新证据改变方案时，可以重新核对这些问题；它们不是固定审批关卡。
评审请求止于发现，除非同时要求实现。需要发布时，另行核对授权与发布后的结果。

[Skill](../../skills/clinx-delivery/SKILL.md)提供 Agent 执行步骤；
可选 CLI 保存约定与本地观察，不运行 Agent。

交付沉淀与独立[知识工作](knowledge.md)共用一套规则。Build、Capture、Organize、Maintain
是知识意图，不是另一套交付阶段。把有用发现放回维护者处，从正常入口检查能否检索到，
复用前重新核对已变化或冲突的结论。

## 先明确含义，再依赖证据

分清三类来源：

- **意图**：原始需求及其授权责任方的决定。
- **现状**：当前代码、契约、运行行为与操作约束。
- **约定**：从现状到目标之间获准实施的改动。

三者不一致时解决冲突。实现、生成的方案或测试没有重新定义需求的权限。

同时核对语义与执行是否充分。测试可能准确验证了错误规则；正确规则也可能因零用例、
错误目标而被误判通过。Agent 与责任方判断含义，确定性工具加强执行证据。

## 调查相关系统

从用户动作或外部事件追踪到最终可观察结果，定位规则与状态所有者、传输层、消费者和测试。
区分需要修改的组件与无需修改但仍须验证的消费者；没有依据的部分保留为未知。

已有地图与指南用于导航到当前来源。缺少文档不代表缺少能力。新增共享逻辑前，
检查相近实现及调用点，包括权限、边界和失败语义。调查足以支持当前选择即可，
不要求先盘点整个仓库。

从工作区的正常入口开始导航，包括相关的已有工具绑定。共享语义改变时，在现有方案内
保留影响记录：当前符号或协议及其责任方、上游入口和下游读者、新旧行为、来源证据和
尚未核实的边界。既沿需求路径调查，也反查改变契约的已有消费者。仓库清单或索引结果
本身不能证明受影响行为已经覆盖。

用这份记录选择验证对象，并在已获授权时进行独立源码审查。审查者结合原始需求与当前
来源挑战方案，再将发现回写到同一方案中修正或明确暂缓的决定。参见
[设计评审指引](../../skills/clinx-delivery/references/design-review.md)。
这不要求另一套文档或 CLI 配置。对于影响共享语义的重要改动，已有且已核验、增量成本低的
关系工具绑定属于影响检查的一部分；没有可靠绑定时，用原生搜索和源码导航完成等价的候选清单。

逐能力判断 **复用、扩展、组合、新建或未知**。新产品可以复用身份与存储，
老服务也可以增加新能力。按语义兼容性、归属、数据形状、授权和运行成本选择；
不兼容的复用可能比小规模新建更危险、更昂贵。

### 不穷举所有情况，也能约束未知

按后果、未知程度和恢复难度决定调查深度。明确必须始终成立的规则及其执行责任方，
再用相关入口、等价表达和失败情形挑战规则。只有语义支持同样处理时才合并等价用例。
当示例测试不足以暴露问题时，使用边界/性质测试、故障注入或小型状态模型；模型验证的
是其假设内的系统，不是完整线上世界。

对于重要效果，从执行规则的接收方反查其他调用方与恢复路径，兼顾新行为和已有义务。
影响记录支持有范围的覆盖声明，不能证明绝对完整。把剩余未知关联到依赖它的动作，
并说明什么证据能解决它。可评审设计可以保留外部决定和未来运行检查；这些缺口仍限制
依赖它们的实现或发布声明。评价作者和审查者时，要使用同一个交付终点。

## 形成可执行约定

明确结果与交付终点、范围、非目标、不变量、重要决定、授权以及验收与证据的对应关系。
小任务可在对话中约定；需要持久化时沿用已有方案或[任务简述](../../templates/workspace/clinx/task-brief.md)，
引用详细推理，不重复抄写。

按改变的含义、未知程度和后果选择约定深度。局部可逆且遵循已定规则的工作可停留在对话中；
改变共享语义时，所有者、消费者和兼容性决策应可审阅；高影响状态或外部效果需要明确性质、
恢复语义及最终进展所依赖的前提。已有约定可能已经提供这些依据；业务名词和仓库数量
不自动要求新文档或再次审批。参见[约定深度](../../skills/clinx-delivery/references/delivery.md#choose-agreement-depth-from-the-changed-meaning)。

不变量必须能被反例推翻，例如：总数与返回行来自同一分页前集合；
客户端字段不能覆盖服务端身份；同一操作重试不能重复不可逆效果。
“正确、健壮”没有说明该观察什么。

重要产品选择由责任方决定，常规实现选择交给 Agent。
新发现改变已确认语义或风险时，取得所需决定，保留不受影响的工作，重核相关证据。

交付终点与确认频率分别约定。例如：“先确认方案，再自主实现与测试；不部署。”
确认关联实际动作、对象、责任人、范围和条件。沉默不是同意，本地记录不执行权限控制。
详见[协作与授权](collaboration.md)。

## 用实际反馈驱动实现

从项目指令、脚本和 CI 找到真实构建、测试与运行路径。审阅钩子和副作用，
确定 cwd、配置、数据、身份与目标。使用已有运行时和已授权的项目准备步骤。
工具存在、可访问、启动成功与行为正确是不同观察。

尽早运行最小完整切片。新应用可以先打通提交、真实 API、持久化与刷新展示；
过滤需求可能只需领域查询与 HTTP 边界。不要为了覆盖每一层而扩张需求。

选择能区分当前未知且成本最低的观察：结构检查、局部规则测试、边界测试或消费者操作。
可能推翻设计的集成未知尽早探测；切片稳定后扩大相关回归，
最终相关修改后覆盖验收与项目要求的检查。

失败时保留观察、定位层次、提出假设、选择区分原因的检查，再修复重测。
零用例查选择；成功提示但状态未变查请求与回读。没有新证据的重复执行不是诊断。
具体步骤见 Skill 的[运行指引](../../skills/clinx-delivery/references/runtime.md)。

## 核验消费者与失败语义

底层测试和 Mock 支持开发，但不能证明其替代的真实边界。
根据需求操作实际消费者，覆盖相关版本与负例；消费者代码未改也可能受到服务端变化影响。

跨边界变更核对生产端与接收端的类型、单位、身份、缺失/null/空值/重置语义及权威状态。
生成或持久化结果需在可信规模和写入中断后仍能正确读取。

随规模增长的工作，要明确响应、时效、容量或成本预算及来源。
有限循环、正数延迟本身不能证明满足约束；预算冲突需要对应产品或操作责任方决定。

异步效果区分已受理、运行中、终态成功/失败与结果未知，也区分无效输入、暂时失败和过期任务。
按提供方真实的幂等、重试与恢复契约，通过结果核对或其支持的同一操作重放解决未知写入，
不能盲目作为新操作提交。
方法不规定通用重试次数或队列架构。详见[交付指引](../../skills/clinx-delivery/references/delivery.md)。

## 按实际范围解释证据

观察相对于输入、目标和断言支持结论。不同证据相互补充，不是高低阶梯：生产 trace
不能替代缺失的授权要求或消费者兼容性检查。按真实声明与交付终点选择观察；设计任务
不需要执行尚未获准的生产动作。CLI 分开处理：

| 问题         | 含义                                     |
| ------------ | ---------------------------------------- |
| 执行         | 对命令是否启动、如何结束，已知什么？     |
| 观察         | 支持的输出格式表示通过、失败还是不确定？ |
| 适用性       | 本地绑定和制品是否仍适用？               |
| 验收声明结论 | 当前适用的观察能否支持全部已声明条件？   |

执行可能未知；证据保存不完整不代表命令未执行。本地通过不能证明遗漏的验收、
远端状态、授权或记录真实性。核对实际断言及其与原始需求的对应关系。
精确语义见 [CLI](cli.md)。

真实原生工具的证据可能支持 CLI 无法聚合的约定结果。分别说明交付判断与 CLI 结论，
不能修改结果让两者一致。见[交付示例](evidence.md#完成交付而不只是获得-cli-通过)。

## 评审与交付

先评审目标和新增概念是否必要，再核对规则/状态归属、复用、共享契约、范围、证据与恢复，
最后看命名、结构和文档。上游假设不必要时，先移除假设，再考虑优化围绕它产生的逻辑。

完成取决于约定终点：

| 终点         | 所需结果                                       |
| ------------ | ---------------------------------------------- |
| 方案         | 语义、方案、风险、验证计划与阻碍               |
| 本地验证     | 当前相关行为和实际测试结果，明确替代依赖       |
| 集成验证     | 已识别目标与版本上的真实跨边界效果             |
| 发布就绪     | 必要集成、配置/迁移、兼容性及恢复条件          |
| 已发布并观测 | 获授权制品在正确目标成功发布，随后核验线上行为 |

这些是结果描述，不是 CLI 内置认证等级。就绪不授予发布权限；
代码、配置和数据可能需要不同恢复动作。

重新核对原始需求和最新决定，交付可用结果、启动/使用/停止方法、证据与剩余限制。
完成已有工具和授权可支持的必要验证，不把它交回为“请人工测试”。
真实受阻时说明缺失决定或访问条件、具体下一步、预期观察与恢复边界。

## 续接与沉淀

一个主 Agent 负责跨工程的结果与集成。只有允许且具有独立边界时才委派，
回收后检查整体效果，而不只汇总完成消息。详见[协作](collaboration.md)。

检查点保存发现、阻碍与下一安全动作。恢复时核对当前输入、决定及相关运行中操作；
旧说明不授权重放。当前环境不可用时仍应保留有用历史。

稳定规则留在领域所有者处，重复失败进入回归测试，可复用操作进入已有工具或指南，
一次性推理留在任务。地图指向维护中的事实，保留来源、限制和重核条件；
没有新增价值时不再创建产物。

对重复且稳定的规则，当总成本低于反复解释时，优先采用能忠实表达规则的既有可执行检查。
验证它既拒绝违规也接受受支持行为，并将预防性检查放在效果发生前。理由、导航和易变政策
可以继续使用文字；机械检查不产生权威。复用或必要交接足以抵偿维护时才投入持久导航，
一次性任务不需要新建知识工程。

在可比任务中测量正确交付、遗漏与错误完成、恢复质量及人和 Agent 的总成本。
按预防的失败与维护成本判断可选机制的价值。
[评测协议](evaluation.md)将这些结果与实现测试分开。
